# A short brief for a specified game

Start with a few sentences. Ask follow-up questions only when a missing answer materially changes the game. Use the JSON template if structured handoff is useful.

1. **Purpose and players:** What should the player experience or learn? Who is it for?
2. **The game itself:** Genre, repeated player action, goal, loss/end condition and approximate session length.
3. **Controls and delivery:** Mouse/touch/keyboard; browser or another supported engine; single HTML or a project; offline requirements; target devices.
4. **Art and sound:** Desired style, references, supplied assets, tone, typography, motion and audio. Explain which references concern style versus exact content.
5. **Language and access:** Language choice, text size/readability, keyboard use and any specific accessibility requirements.
6. **Constraints:** What must be preserved, excluded, fact-checked, licensed or demonstrably true about the mechanics?
7. **Optional services:** Email results, accounts, social publishing or another integration—only if needed.
8. **Task mode:** Plan, build or extend. For extend, identify the existing source and permitted changes.

Separate facts with sources, fictional story choices, and balancing parameters. Do not inherit the café example's theme, palette, menu, language set, email flow or business claims by default.

A useful minimum: “Build a three-minute touch-friendly browser puzzle for teenagers. Players route coloured parcels to matching airlocks. Use flat space-station graphics, English text and original short sounds. Deliver one offline HTML file. No accounts or email.”
