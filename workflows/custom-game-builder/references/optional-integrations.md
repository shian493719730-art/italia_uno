# Optional services — selected after the game brief

All optional modules default off. Their presence in a brief means they can be planned; actual registration, external sending, social posting, access grants or spending still follow the owner's explicit task and the execution environment's permissions.

## Project mailbox

Only relevant when the project needs one. Use the owner's preferred existing mailbox or document an owner-assisted registration flow. The owner handles password, verification, recovery information and terms. No account is created just to run this workflow. Keep credentials and real account records out of public source.

## Email a result, receipt or keepsake

Only order-based games need order receipts; other games may use a completion result or no email. Define the intended content, recipient and purpose. If a project copy is requested, disclose it to the player and keep its recipient in trusted configuration. Use clear consent, prevent obvious repeated submissions and distinguish service acceptance from verified delivery. Unknown outcomes need review before retrying. Keep placeholder services visibly unavailable.

A static browser game needs an appropriate external template service or backend for direct sending; do not embed private mail/API credentials in public JavaScript. Document provider setup first, and connect/test it only when requested. A simulated preview must never appear as a real successful send.

## Social publishing

Use authorised assets and an identified project account. Prepare truthful content, approval/queue state and a duplicate-prevention record. Scheduling is not proof of publication; verify the real post after a live action. Do not invent prices, reviews, endorsements or audience results. Account login and publishing are separate from making the game.

## Why these are separate

A standalone puzzle, educational game or story can be complete without any of these services. Their account requirements should never block the basic game workflow. Keep the generic folder portable; optional service code and provider dependencies belong in the project only when that feature is actually selected.
